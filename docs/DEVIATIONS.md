# Deviations from OpenSSL

rustyssl matches OpenSSL's behavior, including its quirks (README.md, "Compatibility target"),
with one exception: where matching it would be unsafe. Every such case is listed here, with
the reason and the test that pins the behavior down. Each entry names the OpenSSL release it was
checked against.

Most entries cover inputs where OpenSSL corrupts memory or crashes. A program that works with
OpenSSL never depends on them.

## Notes

- **EC multiplications on the curve-specific methods.** `nistp224`, `nistp256`, `nistp521`,
  `nistz256`, and `sm2p256` multiply with their own tables and formulas; rustyssl runs one
  Montgomery ladder per term with the same results in affine coordinates, and hands back the
  Jacobian coordinates (Z = 2) where theirs are Jacobian, affine where theirs are (so the
  random numbers converting them draws are the same). `EC_POINT_get_Jprojective_coordinates_GFp`
  of such a result therefore differs. A point off the curve multiplied by one of these
  methods gives a meaningless point that depends on the formulas, so it differs too (the
  differential probe prints only `offcurve` there).
- **Getting an object identifier by ctrl (`EVP_PKEY_CTX_get0_dh_kdf_oid`).** The translation
  gives the provider no room for the name, so no provider can return one, and the ctrl never
  returns the object. When a provider reports an empty name anyway, OpenSSL then reads the
  caller's `ASN1_OBJECT *` as a string to make an object it never returns; rustyssl skips
  that. The results are the same, 0 or the length 0 (`tests/c/evp_pkey_ops.c`).

- **The version text.** This is the one entry not about memory safety: it's about knowing what
  runs. A vulnerability scanner or an administrator reading `OpenSSL 3.5.9` would apply
  OpenSSL's advisories to rustyssl and miss rustyssl's own. The version numbers
  (`OpenSSL_version_num`, `OPENSSL_version_major`/`_minor`/`_patch`,
  `OPENSSL_VERSION_STRING`) are untouched, so version checks pass. The name goes where
  OpenSSL's man page reserves room "for other parties, such as `+fips`, or `+vendor.1`".
  Parsers that read `OpenSSL x.y.z` from the text still do. The other build information
  (directories, compiler, build date, CPU capabilities) describes rustyssl's build, as a
  differently configured OpenSSL's would describe its own; it isn't a deviation.

- **Items over opaque handles (`RSAPublicKey_it`, `RSAPrivateKey_it`).** OpenSSL describes these
  as SEQUENCEs of the `RSA` structure's own fields. rustyssl's `RSA` is a Rust object with no C
  layout to put templates over, so these items are `ASN1_ITYPE_EXTERN`, and they decode, encode,
  and print through a private shadow structure that has OpenSSL's fields, field names, and items.
  Encodings, error queues (`Field=n, Type=RSAPrivateKey`), and printed text are OpenSSL's
  (`tests/c/rsa_asn1.c`, the probe's `asnd2i`). An application sees the difference only by
  reading the item's own fields (`itype`, `templates`, `tcount`, `size`), and in one more way: a
  key nested inside an application's type starts a new count toward the 30-level nesting limit,
  as OpenSSL's own extern items (`X509_NAME`) do. Test:
  `rsa_asn1::tests::the_key_items_are_extern`.

- **`CRYPTO_aligned_alloc`.** On Linux both libraries use `posix_memalign`, which checks the
  size itself, so only macOS (and other builds without it) differs. The rest of the
  macOS rounding is kept, quirks included: alignment 0 returns null with `*freeptr` set, as
  OpenSSL's does. That's allowed because the alignment must be a power of two.
- **Reentrant allocators.** An application can't normally hit this. It takes a malloc
  function that wraps `CRYPTO_malloc`, which OpenSSL can't run either, or `CRYPTO_malloc`
  itself reached through a different address (a non-PIE executable's PLT entry, say).
- **`ERR_add_error_txt`.** Its text often comes from outside, such as a peer's or a
  configuration file's, so OpenSSL's endless loop can be a denial of service. Where OpenSSL
  returns, rustyssl splits the text exactly as it does, separator quirks included (the
  differential probe compares them). The probe's random text never contains a piece that
  long, because the reference would hang.
