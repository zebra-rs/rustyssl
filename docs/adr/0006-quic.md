# ADR 0006: QUIC — a TLS seam, a sans-IO transport, and OpenSSL's QUIC objects in capi

- **Status:** Accepted, 2026-10-20 (implementation plan Phase 10)

## Context

OpenSSL 3.6.5 ships about 37,000 lines of QUIC (`ssl/quic/`): a TLS adapter (`quic_tls.c`), a
record layer and packetiser, ACK management and NewReno, streams and flow control, connection
IDs, ports and engines, and the API layer (`quic_impl.c`). Applications reach it three ways:

- **The QUIC API** (10.2): `OSSL_QUIC_client_method` and `_client_thread_method` (3.2),
  `OSSL_QUIC_server_method` with listeners and domains (3.5), stream objects, `SSL_handle_events`,
  `SSL_get_event_timeout`, blocking and non-blocking I/O, `SSL_poll`, `SSL_get_value_*`.
- **The third-party QUIC stack API** (10.3, 3.5): `SSL_set_quic_tls_cbs` turns an ordinary TLS
  `SSL` into the handshake engine of someone else's QUIC (ngtcp2's `ossl` backend), through six
  callbacks (`OSSL_FUNC_SSL_QUIC_TLS_*`, core_dispatch.h).
- **Tests and interop** that observe errors, stream states, and close codes.

ADR 0002's core (`rustyssl-tls`) is sans-IO and yields at every observable event; QUIC must
keep that, keep `unsafe` out of the core (rule 1), and never hold a lock across a callback
(rule 7).

## Decision

### 1. The TLS↔QUIC seam: a QUIC mode on `rustyssl_tls::Connection`

QUIC uses only TLS 1.3's handshake. The core gains a mode, in a new module
`rustyssl-tls/src/conn/quic.rs`, that both 10.3 and the transport drive:

```rust
// rustyssl_tls::conn::quic
/// OpenSSL's protection levels (OSSL_RECORD_PROTECTION_LEVEL_*, from rustyssl_abi).
pub enum QuicLevel { Initial, Early, Handshake, Application }
pub enum Direction { Read, Write }               // 0 and 1 in the C callback

pub struct QuicTlsConfig {
    pub transport_params: Option<Vec<u8>>,      // SSL_set_quic_tls_transport_params
    pub early_data: bool,                        // SSL_set_quic_tls_early_data_enabled
}

pub struct QuicSecret {
    pub level: QuicLevel,
    pub direction: Direction,
    pub suite: &'static crate::suites::Cipher,   // the negotiated (or early) TLS 1.3 suite
    pub hash: crate::crypto::HashAlg,
    pub secret: crate::crypto::Secret,           // zeroized on drop
}
```

- **Enabling it:** `Config::quic: Option<QuicTlsConfig>`. When set, the core behaves as
  `quic_tls.c` makes libssl behave. The minimum version is TLS 1.3, middlebox compatibility is
  off, and ChangeCipherSpec is neither sent nor accepted. There is no EndOfEarlyData. A received
  KeyUpdate fails with unexpected_message, and `SSL_key_update` fails, because QUIC changes keys
  with key phases. Tickets carry `max_early_data` 0xffffffff when early data is on (RFC 9001
  4.6.1). ALPN is required: a client without one fails before starting, and a handshake that
  negotiates none fails. Both cases raise exactly what `quic_tls.c` raises (lines 796–850).
- **No record layer.** Handshake bytes enter with
  `Connection::feed_quic_crypto(level: QuicLevel, data: &[u8]) -> Result<()>`. Bytes at a level
  other than the current read level are refused, as RFC 9001 4.1.3 requires. Output comes from
  `Connection::take_quic_crypto() -> Vec<(QuicLevel, Vec<u8>)>`, each chunk tagged with the
  write level current when it was produced. `Event::Output` means crypto data is waiting.
  `read_level()` and `write_level()` report the current levels. The core stores no keys for
  these levels: the `install13` points in `conn/common/keys.rs` yield secrets instead.
- **Secrets are events:** `Event::QuicSecret(QuicSecret)` is emitted at each point where
  TLS-over-TCP would install keys, in OpenSSL's order. That covers client early write, then
  handshake read and write, then application read and write, and their server counterparts. The
  Initial level never comes from TLS; QUIC derives it from the DCID.
- **Transport parameters** use extension 57 (`TLSEXT_TYPE_quic_transport_parameters`).
  - **Sending:** it goes in the ClientHello and the EncryptedExtensions, holding
    `QuicTlsConfig::transport_params`.
  - **Receiving:** the peer's extension raises `Request::QuicTransportParams { params: Vec<u8> }`.
    The caller answers `Answer::Continue`, after setting its own parameters through
    `config_mut()` if it is a server that waited, or `Answer::Fail`. The callback's 0 is fatal.
  - **Missing:** a missing extension fails with `missing_extension`.
- **Alerts aren't written.** When the core would send one, `step` returns its `Err` as today.
  The alert's description is `Error::alert`, which the caller turns into `alert_cb` (10.3) or
  CRYPTO_ERROR 0x100+alert (10.2). This applies after the handshake too.
- **Post-handshake:** NewSessionTicket goes in and out at the Application level.
  `read_app` never returns data in QUIC mode.
- **Cipher suites are not filtered.** The TLS configuration's suites stay as they are. OpenSSL's
  own QUIC supports only AES-128-GCM, AES-256-GCM and ChaCha20-Poly1305: a CCM suite fails at
  the first secret with internal_error and `SSL_R_UNKNOWN_CIPHER_TYPE` (`quic_tls.c`), and the
  transport reproduces that. The third-party API passes any suite through.
- **What stays as it is:** every existing Request and callback (verify, ALPN select,
  servername, PSK, tickets, keylog, info and msg callbacks). They work unchanged, so the
  application sees the same callbacks over QUIC.

### 2. `rustyssl-quic`: a sans-IO transport

A new crate, `crates/rustyssl-quic`, has `#![forbid(unsafe_code)]` and denies `unwrap_used`,
`expect_used` and `indexing_slicing`. It depends on `rustyssl-tls` (the QUIC-mode `Connection`,
`keysched::expand_label`/`hkdf_*`, `crypto::Provider`) and nothing C.

- **Time and addresses are inputs.** `Time` is a monotonic `u64` of nanoseconds supplied by the
  caller (OpenSSL's `OSSL_TIME`). A peer address is `PeerAddr(Vec<u8>)`, the `BIO_ADDR` bytes,
  compared and never interpreted beyond its family.
- **Crypto:** `rustyssl_quic::crypto::Provider: rustyssl_tls::crypto::Provider` adds
  `fn header_protection(&self, alg: HpAlg, key: &[u8]) -> Result<Box<dyn HeaderProtection>>`,
  where `HeaderProtection::mask(&self, sample: &[u8; 16]) -> [u8; 5]`. AES uses one ECB block,
  ChaCha20 the raw keystream. capi implements it with EVP; the tests use `rustyssl-crypto`.
- **Modules,** after OpenSSL's split, which keeps the tests comparable:
  - `wire`: varints, long and short headers, every RFC 9000 frame, transport parameters.
  - `packet`: protection, packet numbers, coalescing, the RFC 9001 Initial salt and the
    "quic key/iv/hp/ku" labels, key phases.
  - `ackm`: received ranges, ack delay, RFC 9002 loss detection and PTO.
  - `cc`: NewReno, as `cc_newreno.c`.
  - `stream`: send and receive buffers, reassembly, the stream map and states.
  - `fc`: connection and stream credit with `quic_fc.c`'s window auto-tuning.
  - `cid`: local and remote connection IDs, retirement, stateless reset tokens.
  - `txp`: the packetiser, which orders frames per packet-number space.
  - `channel`: one connection. It owns the QUIC-mode `Connection` and runs the handshake,
    idle timeout, closing and draining.
  - `port`: one socket's demux by DCID. A server port does Retry with address-validation tokens
    (an AEAD key per port), version negotiation (only QUIC v1, as OpenSSL), and an accept queue.
- **Driving API:**

  ```rust
  impl Port {
      pub fn new(cfg: PortConfig) -> Self;
      pub fn handle_datagram(&mut self, p: &dyn Provider, now: Time, from: &PeerAddr, data: &[u8]);
      pub fn poll_transmit(&mut self, p: &dyn Provider, now: Time) -> Option<(PeerAddr, Vec<u8>)>;
      pub fn next_timeout(&self) -> Option<Time>;
      pub fn handle_timeout(&mut self, p: &dyn Provider, now: Time);
      pub fn poll_event(&mut self) -> Option<PortEvent>;
      pub fn channel(&mut self, id: ChannelId) -> Option<&mut Channel>;
  }
  impl Channel {
      pub fn connect(...);
      pub fn stream_open(&mut self, bidi: bool) -> Result<StreamId>;
      pub fn stream_send(&mut self, id: StreamId, data: &[u8], fin: bool) -> Result<usize>;
      pub fn stream_recv(&mut self, id: StreamId, buf: &mut [u8]) -> Result<(usize, bool)>;
      pub fn stream_reset(&mut self, id: StreamId, code: u64) -> Result<()>;
      pub fn stream_stop_sending(&mut self, id: StreamId, code: u64) -> Result<()>;
      pub fn accept_stream(&mut self) -> Option<StreamId>;
      pub fn shutdown(&mut self, app_error: u64, reason: &[u8]);
      pub fn tls_answer(&mut self, a: rustyssl_tls::conn::Answer);
  }
  ```

- **Channel events** (`ChannelEvent`):
  - `TlsRequest(Request)`, answered with `tls_answer`;
  - `TlsInfo(Event)`, for the info, msg and keylog callbacks;
  - `HandshakeComplete`;
  - `IncomingStream`;
  - `StreamReadable(id)` and `StreamWritable(id)`;
  - `Terminated(TerminateCause { remote, app, code, frame_type, reason })`.
- **Bounds** (rule 5):
  - **Taken from OpenSSL:** ACK ranges per frame; frames per packet; reassembly bounded by the
    flow-control window; at most `active_connection_id_limit` connection IDs; the token length;
    each transport parameter's length; the coalesced packets in one datagram; buffered
    out-of-order CRYPTO data per level.
  - **Our own:** where OpenSSL has no cap, we set one and record it in `docs/DEVIATIONS.md`.
- **Defaults** come from OpenSSL's sources: the initial windows, stream counts, idle timeout
  (30 s), ack delay exponent, and `disable_active_migration`. OpenSSL 3.6 supports no active
  migration, and neither do we. A probe of the reference settles each value.

### 3. capi: OpenSSL's QUIC objects

- **One `SSL` handle, several kinds.** The `SSL` handle gains a kind, as OpenSSL's
  `SSL_TYPE_*` distinguishes them: TLS connection, QUIC connection, QUIC stream, QUIC listener,
  QUIC domain. Every `rustyssl_private_SSL_*` dispatches on it the way `quic_impl.c` does for
  `IS_QUIC`. The QUIC-API functions now in `ssl/misc.rs` keep their TLS-object behavior, and gain
  the QUIC paths.
- **Ownership:**
  - a domain (engine) owns ports;
  - a listener or a client connection owns a port, which owns channels;
  - stream `SSL`s hold a reference to their connection.

  A connection's default stream (`SSL_set_default_stream_mode`) lives in the connection object.
- **Locking: one mutex per engine,** shared by its ports, connections and streams. This is
  OpenSSL's contentive model (CCM); WCM isn't in 3.6. Every API call follows the TLS driver's
  pattern from ADR 0002: lock, mutate, collect pending callbacks, unlock, run them, relock and
  answer. No lock is ever held while a callback runs, including verify, ALPN, servername, keylog,
  info, msg and the 10.3 callbacks.
- **Network I/O** goes through the connection's or listener's datagram BIO: `BIO_s_datagram`,
  `BIO_s_dgram_pair`, or an application BIO with `BIO_sendmmsg`/`BIO_recvmmsg`. A tick runs
  `recvmmsg` into the port, handles the timeouts, then sends with `sendmmsg`.
  - **Calls:** `SSL_handle_events` performs one tick, and `SSL_get_event_timeout` returns
    `next_timeout`.
  - **Blocking:** blocking calls need a BIO that offers poll descriptors
    (`BIO_get_rpoll_descriptor`), as in OpenSSL. They tick, then `poll(2)` the descriptors with
    no lock held, until the call can finish or the timeout passes.
- **Thread-assisted mode** (`OSSL_QUIC_client_thread_method`): a `std::thread` per connection
  ticks it at `next_timeout` under the engine mutex. A condvar wakes it when the deadline moves,
  and the connection's free joins it.
- **`SSL_poll`** evaluates each item's readiness under its engine's lock, as `SSL_poll(3)`
  defines it, then ticks and waits like a blocking call. `SSL_get_value_*` and `SSL_set_value_*`
  map their `SSL_VALUE_*` ids to the channel's settings.
- **10.3 lives in `ssl/quic_tls.rs`:** `SSL_set_quic_tls_cbs` on a TLS `SSL` sets `Config::quic`
  and stores the dispatch table, read with bounds as ADR 0003 reads provider tables. The TLS
  driver then:
  1. calls `crypto_send` with each `take_quic_crypto` chunk, looping on `consumed`;
  2. on reads, calls `crypto_recv_rcd`, copies the record into `feed_quic_crypto`, then calls
     `crypto_release_rcd` with the same length;
  3. maps `QuicSecret` to `yield_secret`, `Request::QuicTransportParams` to
     `got_transport_params`, and an `Err` carrying an alert to `alert`.

  Every callback runs with no lock held; a 0 return is fatal, as `SSL_set_quic_tls_cbs(3)` says.

### 4. Tests

- **Vectors:** RFC 9001 Appendix A (Initial keys, the client and server Initial packets, Retry,
  ChaCha20 short header) are unit tests in `rustyssl-quic`, as are RFC 9000's varint examples.
- **Loopbacks:** a client channel against a server channel in-process, with seeded loss,
  duplication and reordering (as `conn::pair` and the DTLS relay do), and a TLS-only QUIC-mode
  pair in `rustyssl-tls`.
- **Fuzz targets** (`fuzz/fuzz_targets/`): `quic_packet` (unprotect and parse), `quic_frames`,
  `quic_transport_params`, `quic_tls` (QUIC-mode TLS fed arbitrary CRYPTO data), `quic_port`
  (datagrams into a server port).
- **C conformance** (`tests/c/`): every newly implemented export, run on both libraries, client
  and server in one process over `BIO_s_dgram_pair` (3.5's server API makes this possible).
  - `ssl_quic_tls.c` pairs two TLS `SSL`s through the 10.3 callbacks.
  - Secrets are printed only as hashes; the timing values that can't match are masked.
- **Upstream tests:**
  - `quicapitest`, `quic_multistream_test` and `quic_client_test` go into
    `tests/openssl-suite/ssl.txt` and `recipes.txt`, replacing the "Phase 10" skips.
  - Tests that reach OpenSSL internals are marked `internal` with reasons: the module unit tests
    (`quic_ackm_test`, `quic_txp_test`, ...), `quic_tserver_test`, `quicfaultstest`'s fault
    injector, and the fake-time hooks.
- **Interop** (`cargo xtask test-quic-interop`):
  - **Peers:** ngtcp2 (its OpenSSL-QUIC client and server), quiche's apps and quic-go's
    examples, each built from pinned, SHA-256-verified sources under `target/`.
  - **Cases:** a local driver runs quic-interop-runner's core cases (handshake, transfer, retry,
    resumption, zerortt, chacha20, keyupdate, multiplexing) with its HTTP/0.9 file-transfer
    checks, in both directions and on both libraries.
  - **Why not the runner itself:** it needs Docker images of several GB each, and this
    machine's Docker disk has about 2 GB free. It can run in CI or a larger host later.
- **Consumers:** `test-consumers` gains `curl-h3` (curl built with `--with-openssl-quic` and
  nghttp3, its HTTP/3 tests on both libraries) and `ngtcp2` (its `ossl` backend's tests, for
  10.3).

### 5. Order and split

Three forks own disjoint files:

- **A, the seam and 10.3:** `rustyssl-tls` (`conn/quic.rs`, and the hooks in `conn/mod.rs`,
  `conn/common/keys.rs`, `conn/common/ext.rs`, `conn/statem.rs`, `conn/event.rs`); capi
  `ssl/quic_tls.rs` plus the driver's QUIC-mode branch in `ssl/io.rs`; `tests/c/ssl_quic_tls.c`;
  the `ngtcp2` consumer.
- **B, the transport:** all of `crates/rustyssl-quic`, written against a small trait of its own
  (`quic::Handshake`, with feed, take, events and answers) and a test double, until A lands. Also
  the new file `crates/rustyssl-capi/src/ssl/quic_provider.rs` (EVP header protection), the
  `quic_*` fuzz targets, the RFC vectors, and one workspace line in `Cargo.toml`.
- **C, the API (10.2), after A and B merge:** capi `ssl/quic/` (objects, engine mutex, reactor,
  streams, listener and domain, `SSL_poll`, values), the QUIC paths in `ssl/misc.rs` and
  `ssl/method.rs`, the upstream QUIC programs in the suite harness, and `test-quic-interop` and
  `curl-h3`. The interop and curl work can be a fourth fork, D, in parallel with C.

### 6. Decisions during implementation (2026-10-20)

The user decided two things:

- **Interop exit.** Phase 10's interop exit is the local `test-quic-interop` driver (fork D)
  against ngtcp2, quiche and quic-go, running quic-interop-runner's core cases. The Docker
  quic-interop-runner itself is a follow-up, for a host with the disk it needs.
- **Upstream tests that need OpenSSL's internals are excluded as `internal`.** Upstream's QUIC
  programs are built around OpenSSL's internal QUIC: the module unit tests
  (`quic_ackm_test`, `quic_txp_test`, ...), the test server (`ossl_quic_tserver_*`), its fault
  injector, and its fake time. No other library can provide those. The exclusions are:
  - all of `quic_multistream_test`, whose scripts, `test_dyn_frame_types` included, run
    against the test server with internal threads and packet writers;
  - `quicapitest`'s tests that build their server with `qtest_create_quic_objects` (the test
    server) or read the channel, port, packetiser or record layer (102 of 118 subtests). Its
    16 other subtests use only the public API and pass;
  - `quic_tserver_test`, `quicfaultstest` and the QUIC fuzz recipes, which import internal
    functions; `test-openssl-suite --all` finds these from the programs.

Choices made while building 10.2:

- A connection is its own handshake layer and reuses the 10.3 path. The transport's
  `Handshake` is a pair of queues that the TLS driver fills between ticks, with no lock held,
  so the application's callbacks run as over TCP.
- A domain's listeners keep one engine each, rather than sharing the domain's. The domain
  ticks them all. Behavior is the same; only lock granularity differs.
- `s_server` has no QUIC mode in 3.6.5. So `test-interop --peer quic` pairs OpenSSL's guide
  QUIC demo servers with the guide's clients and `s_client -quic`, on both libraries.

## Consequences

- One TLS implementation serves TCP, DTLS, OpenSSL's QUIC and third-party QUICs. The
  application's callbacks and errors are the same in all four.
- The transport is safe Rust, fuzzable and testable with no C. All `unsafe` stays in capi's
  object, BIO and thread code.
- A per-engine mutex matches OpenSSL's model and its throughput limits. A worker model would be
  a later change, as it is upstream.
- Interop beyond what builds locally (the Docker runner, more peers) waits for disk or CI
  capacity.
